Lecture 2 · WhatsTheTime.com · PDF p. 230-240 (part p. 3-13)

Stateless web app: WhatIsTheTime.com er journey

Shohoj kore: App ta shudhu bole "ekhon koyta baje". Kono database nai, protita server nijei time jane. Tai eta stateless: je kono server je kono user ke uttor dite pare. Shuru choto (downtime cholbe), pore vertical ar horizontal scale, downtime chara.

Requirement (PDF p. 230 (part p. 3))

  • Manush ke time jananor app; database lage na.
  • Shuru choto, downtime accept kora jay.
  • Pore puro vertical ar horizontal scale, no downtime.

Dhap 1: Starting simple (PDF p. 231 (part p. 4))

Dhap 1
User"What time is it?"→ Elastic IP→ Public EC2t2.micro

Ekta public t2.micro, sathe Elastic IP. Eta prothom PoC.

  • Keno Elastic IP: instance restart/kichu holeo static IP thakuk (EIP Section 06 e).
  • Problem: user barche, t2.micro e ar kulay na.

Dhap 2: Scaling vertically (PDF p. 232 (part p. 5))

Dhap 2
Users ×3→ Elastic IPsame IP→ Public EC2t2.micro → m5.large

Instance stop → instance type bodlao → start. IP same thake karon Elastic IP.

  • Ki add: boro instance (M5) = vertical scaling.
  • Bhalo: Elastic IP thakay user same IP tei pay.
  • Problem: M5 e upgrade korar somoy downtime; user app access korte pareni.

Dhap 3: Scaling horizontally, protita EC2 te Elastic IP (PDF p. 233 (part p. 6))

Dhap 3
Users3 ta IP mone rakhte hoy→ EIP 1 → M5 EIP 2 → M5 EIP 3 → M5

3 ta m5.large, protita te alada Elastic IP = horizontal scaling.

  • Problem 1: user ke protita Elastic IP er exact value jante hoy; IP barle aro jhamela.
  • Problem 2: beshi infrastructure manage.
  • Problem 3: default e proti region proti account e 5 ta Elastic IP; beshi na.

Dhap 4: Route 53 A record, Elastic IP bad (PDF p. 234 (part p. 7))

Dhap 4
User→ DNS query Route 53api.whatisthetime.com
A record, TTL 1 hour→ IP list Public EC2 ×3No Elastic IP

A record = hostname → IP. User Route 53 theke IP gulo pay, tarpor sorasori EC2 te jay.

  • Ki add: Route 53, A record (TTL 1 hour). Mone rakho: A record = IP (Section 10 e).
  • Bhalo: Elastic IP manage korte hoy na. Instance er IP bodlale Route 53 record update kore sync rakho.

Dhap 5: Instance add/remove korle TTL er problem (PDF p. 235 (part p. 8))

Dhap 5
UserIP cache kora, TTL 1 hour→ Public EC2INSTANCE IS GONE!

Ekta instance remove korlam, kintu user er kache purono DNS answer 1 ghonta valid.

  • Problem: TTL 1 hour, tai user 1 ghonta dhore muchhe jawa instance er IP te connect korar cheshta kore. User bhabe app down.
  • Shiksha: DNS A record diye instance add/remove (scaling) bhalo chole na.

Dhap 6: Load balancer + health check, private EC2 (PDF p. 236 (part p. 9))

Dhap 6
User→ Route 53Alias record→ ELB + Health Checkspublic, AZ 1→ SG restricted Private EC2 ×3m5.large, AZ 1

EC2 ar public na. Shob traffic ELB diye. EC2 er security group shudhu ELB er SG theke traffic ney.

  • Ki add: ELB (public facing) + health checks; EC2 gulo private, manually launch, ek-i AZ e ("because we don't know any better").
  • Health check: instance down/kaj na korle oikhane user traffic jay na.
  • Security group: ELB ar EC2 er moddhe traffic restrict, SG reference diye (Section 08 e).
  • DNS: ekhon A record cholbe na, karon load balancer er IP sob somoy bodlay. Tai Alias record → ELB.
  • Bhalo: instance add/remove kore LB te register korle user er downtime nai (health check er jonno).
  • Problem: instance manually add/remove kora kothin.

Dhap 7: Auto Scaling Group (PDF p. 237 (part p. 10))

Dhap 7
Route 53Alias→ ELB + Health Checks→ Auto Scaling GroupAZ 1, private EC2

Ekhon ASG nije demand onujayi instance barabe-komabe.

  • Ki add: ASG: scale out / scale in on demand (sokale keu time jante chay na, shondhay office chharar somoy sobai chay).
  • Bhalo: no downtime, auto scaling, load balanced. Cost o bhalo: shob somoy "perfect" sonkhok instance.
  • Problem: shob kichu AZ 1 e. Earthquake e AZ 1 gele puro app down.

Dhap 8: Multi-AZ (PDF p. 238 (part p. 11))

Dhap 8
Route 53Alias→ ELB + Health Checks + Multi AZAZ 1 to 3→ ASG: AZ 12 instance ASG: AZ 22 instance ASG: AZ 31 instance

ELB ar ASG duitai onek AZ jure. Ek AZ gele baki AZ traffic serve kore.

  • Ki add: ELB multi-AZ (AZ 1-3), ASG onek AZ span kore.
  • Bhalo: app highly available ar resilient to failure.

Dhap 9: Minimum 2 AZ, capacity reserve (PDF p. 239 (part p. 12))

Dhap 9
ASG minimum capacity= Reserved Instances= Cost savings

Je instance gulo sara bochor cholbei (ASG er minimum), segulo reserve koro.

  • Jani kompokkhe 2 ta instance (protita AZ e ekta) sob somoy cholbe → oigulo Reserved Instance = future e onek cost saving.
  • Scale out e notun instance gulo temporary → On-Demand thik ache.
  • Aro sosta chaile Spot, kintu Spot instance terminate hote pare (purchasing option Section 05 e).

Ei lecture e ki ki dekhlam (PDF p. 240 (part p. 13))

  • Public vs private IP ar EC2 (architecture e kothay).
  • Elastic IP vs Route 53 vs Load Balancer.
  • Route 53 TTL, A record ar Alias record: TTL er jonno A record dia scaling hoy na → LB + Alias.
  • EC2 manually maintain vs Auto Scaling Group (on-demand scale, better costing).

Exam: ASG min = 2 (HA er jonno), aro cost komao → oi 2 ta instance Reserve koro; min 1 ba 0 korle HA bhange, ALB soriye EIP dile scaling/HA jay (U11-Q1). "Instance IP bodlay / onek instance, ek nam chai" → ELB + Route 53 Alias, A record na (LB er IP bodlay). DNS TTL beshi + instance remove = user purono IP te atke thake. "AZ failure survive" → ELB + ASG multi-AZ. EC2 shudhu LB theke → EC2 SG source = LB er SG.

Subtitle e "three and five large instances" = 3 ta M5 large dhorechi (slide er M5 onujayi).

Lecture 3 · MyClothes.com · PDF p. 241-251 (part p. 14-24)

Stateful web app: MyClothes.com (shopping cart, session, database)

Shohoj kore: Supermarket e tumi trolley te jinish rakho. Protibar onno counter er lok tomake serve korle, trolley jodi ager counter e pore thake, tumi jinish haraba. Tai trolley ta hoy tomar haate (cookie), ba ekta common locker e (ElastiCache/DynamoDB), jekhane je kono counter tomar token number (session_id) diye khule dekhte pare. Tahole counter (EC2) gulo "kichu mone rakhe na" = stateless web tier.

Requirement (PDF p. 241 (part p. 14))

  • Online e kapor kena; ekta shopping cart ache.
  • Ek shathe hundreds of users.
  • Scale korte hobe, horizontal scalability rakhte hobe, web application joto somvob stateless.
  • User er shopping cart harano cholbe na.
  • User er details (address etc.) database e thakbe, jekono jayga theke access.

  • User bhabe bug; abar try kore; abar onno instance; "MyClothes.com is a bad website" → tk haralam.

Dhap 1

  • Problem: oi EC2 kono karone terminate holeo cart harabe.

Dhap 2: User cookies (PDF p. 244 (part p. 17))

Dhap 2

Cart EC2 te na, user nijei rakhe ar protibar pathay.

  • Bhalo: stateless: kono EC2 ke ager kotha mone rakhte hoy na. Onek web framework ei pattern use kore.
  • Problem 1: HTTP request bhari hoy (cart barle cookie barbe).
  • Problem 2: security risk: attacker cookie bodlate (alter) pare → EC2 ke cookie content validate korte hobe.

Dhap 3: Server session: session_id + ElastiCache (PDF p. 245 (part p. 18))

Dhap 3

EC2 #1 cart ElastiCache e likhe (key = session_id). EC2 #2 same session_id diye pore niye ase.

  • Ki add: cookie te shudhu choto session_id; cart data thake ElastiCache e.
  • ElastiCache sub-millisecond performance → sob khub druto.
  • Alternative: session data DynamoDB te (DynamoDB Section 19 e detail).
  • Beshi secure: ElastiCache = source of truth; attacker ElastiCache er data bodlate pare na. Khub common pattern.

Dhap 4: User data RDS e (PDF p. 246 (part p. 19))

Dhap 4

RDS = long-term storage. Protita EC2 RDS e kotha bolte pare, tai web tier stateless thake.

User beshi read kore (product info dekhe). Write master e, read replica theke.

Ei lecture e ki ki dekhlam (PDF p. 251 (part p. 24))

Web app er 3-tier architecture: client tier, web tier, database tier.

  • Security group gulo ek-ekjon ke reference kore → tight security.
  • Trade-off: cost bare (Multi-AZ chaile, read scale chaile beshi dam), kintu jene-shune decision.

Lecture 6 · Beanstalk Overview · PDF p. 261-267 (part p. 34-40)

Elastic Beanstalk: shudhu code dao, baki AWS banabe

Shohoj kore: Restaurant khulte chao. Nije building, kitchen, gas line, staff setup na kore, ekta food court e stall nao: jayga, light, pani, cleaning ready; tumi shudhu ranna (code) koro. Tobe chaile stall er sob setting nije bodlate paro. Beanstalk oi food court: ELB + ASG + EC2 + RDS er chena architecture tomar hoye banay.

Overview (PDF p. 263 (part p. 36))

  • Ager sob component reuse kore: EC2, ASG, ELB, RDS, ...

  • Developer er daitto shudhu application code.
  • Tobu configuration er upor full control thake (sob component ek interface e bundled).
  • App update korar sundor upay ache.
  • Beanstalk nije free; underlying instance, ASG, ELB etc. er dam dite hoy.
