Summary

Big picture

App gulo kotha bole duivabe: synchronous (Buying service shorashori Shipping service ke call kore) ba asynchronous / event based (majhe queue; ek jon message rekhe jay, arek jon nijer shomoy e tule ney). Synchronous e hothat spike (shadharon 10 ta video, aj 1,000) hole receiver overwhelmed. Tai majhe decoupling layer boshao, je nije scale kore.

Tin ta model: SQS = queue model (pull, ek message ek consumer), SNS = pub/sub model (push, sobai copy), Kinesis = real-time streaming model (big data, order, replay). Ar on-prem er open-protocol broker code na bodlai cloud e anle Amazon MQ.

Majhe layer thakle producer ar consumer alada scale kore; spike e request harabe na.

Exam: "decouple", "sudden spike", "requests / orders lost", "tightly coupled monolith", "timeouts" dekhlei age SQS bhabo.

SQS Standard queue

Shohoj kore: Post office er chithir baksho. Je keu chithi phele (producer), pion ra (consumer) baksho theke tule ney (poll), kaaj kore, tarpor phele dey (delete). Baksho kokhono bhore na, kintu chithi 4 din (max 14 din) por nije nosto hoy. Majhe majhe ek chithi duijon pion er hate jay (duplicate), ar order er guarantee nai.

Security: in-flight HTTPS API; at-rest KMS. Console e default encryption SSE-SQS (S3 er SSE-S3 er moto); option SSE-KMS. Client-side encryption client nije kore, SQS out of the box kore na.

Access control: IAM policy SQS API access thik kore. SQS access policy = resource policy (S3 bucket policy er moto): cross-account access, ar SNS ba S3 event ke queue te likhte dite. EC2 consumer e IAM role; on-prem server e IAM user credentials (role attach kora jay na).

Hands-on: message details e receive count; Purge = shob message muche dey (dev e, prod e na); monitoring e approximate age of oldest message (ASG scale er arekta metric).

Exam: Traffic 100x, SQS Standard e ki korbe → kichu na, SQS nije scale kore. "Standard queue order preserve kore" = false; "at-least-once delivery" = true. Default retention e weekly batch job → kichu message nai (4 din por delete). Retention max (14 din) e 13 din por crash → message ekhono ache, restart e process hobe. Onno company / account queue poll korbe → SQS access policy. Transcoding job SQS e keno → horizontal scaling of workers (order guarantee na).

SQS FIFO queue

Shohoj kore: Bank er token: je order e token, shei order e dake. Ek line er gotir shima ache (300 msg/s). Ek-i token duibar dile (5 min er moddhe same deduplication ID) queue nije phele dey. Order thake message group er bhitore: protita group nijer line.

FIFO
Producer4, 3, 2, 1→ DemoQueue.fifo→ Consumer4, 3, 2, 1 (same order)
Order per Message Group ID
Group = desktop-AA1, A2, A3 in order Group = desktop-BB1, B2 in order→ Alada consumer parallel e

Joto group, toto parallel consumer; group er bhitore strict order.

  • Ordering: strict, Message Group ID level e; group ID protita message e mandatory.
  • Exactly-once send: Deduplication ID; same ID 5 min er moddhe abar ashle duplicate remove. Ba setting content-based deduplication (body same hole).
  • Throughput limited: 300 msg/s batching chara, 3,000 msg/s batching e.
  • Naam .fifo diye shesh hote hobe, na hole create hoy na.
  • Question theke (course e nai): Standard → FIFO convert hoy na, delete kore notun FIFO queue banao. S3 event notification Standard SQS e jay, FIFO SQS e na.
Exam: "Exactly once + in order" → SQS FIFO (Standard, DLQ, delay queue na). Checkout timeout e form abar submit, duplicate order → order DB te, order number SQS FIFO e. Form "exactly once, no data loss" → FIFO. 1,000 msg/s + order → FIFO + batch (4 msg per call = 1,200/s). Per-desktop order, consumer = desktop shonkha → FIFO + Group ID = desktop ID. Payment ID onujayi order (2 answer) → KDS partition key = payment ID ar FIFO group = payment ID. Migration checklist: delete + recreate, .fifo, batching e 3,000 msg/s er beshi na.

SQS + Auto Scaling: buffer ar tier decoupling

Shohoj kore: Line lomba hole beshi worker dako, chhoto hole kombe. Sale er din DB te shorashori likhle DB hapiye transaction fail; tai age order queue te rakho (harabe na), worker group dheere DB te likhbe. Dump e shobcheye beshi asha pattern.

Decouple application tiers
Front-end ASGrequest ney→ SQS→ Back-end ASGvideo process, GPU instance→ S3

DB te insert confirm hole tobei delete, tai kono transaction harabe na. Shorto: client er tokhon-i write confirmation lagbe na.

  • Front-end ar back-end alada ASG, alada scale: front-end traffic e, back-end queue backlog e; protita tier e optimal instance type (back-end e GPU).
  • Question theke: best policy target tracking on custom metric backlog per instance (ApproximateNumberOfMessages ÷ InService instance). Simple scaling cooldown e wait kore, scheduled scaling unpredictable spike dhore na.
  • Async job, client wait korte raji, retry chole, cheapest → SQS + Spot worker. Baseline shob shomoy + downtime nai → Reserved (baseline) + On-Demand (extra).
  • Priority SQS e nai → duita queue (premium / free), worker age premium queue poll kore.
  • Hybrid decoupling (EC2 + on-prem): SQS ba SWF (Simple Workflow Service; course e nai, legacy, aj Step Functions): multi-step checkout, distributed business process. Purono question e "order duibar process" er fix SWF (option e FIFO chilo na); aj SQS FIFO.
  • Microservices (ECS) er moddhe communication → SQS. Spike + ordered process + independent component → Fargate + RDS + SQS.
Exam: "Jobs / requests lost", "variable / unpredictable load", "Aurora bottleneck on promotion", "CPU 100%, queue bhore jay", "invitation deri te ashe", "durably stored jobs, loosely coupled" → SQS + ASG scaling on queue depth (AMI + launch template + ASG). Trap: CPU / network metric, scheduled scaling, boro instance, ALB / ELB pre-warm (request store kore na), SNS (job store kore na).

SNS (pub/sub)

Shohoj kore: WhatsApp group: ekbar message dao, shob member copy pay. Notun receiver jog korle producer er code bodlate hoy na (direct integration e protibar notun integration likhte hoto). Kintu offline member er message SNS dhore rakhe na: persist kore na, deliver na hole harate pare.

Prottek subscriber topic er shob message pay (filter policy na thakle). Kinesis Data Streams subscriber hote pare na; Firehose pare.

  • Limit: 12,500,000 subscription per topic, 100,000 topic per account (barano jay; limit niye exam e proshno ashe na).
  • Publish: Topic publish (SDK: topic → subscription → publish) ba Direct publish mobile app er jonno (platform application → platform endpoint → publish; Google GCM, Apple APNS, Amazon ADM).
  • Hands-on: Email subscription "pending confirmation" thake, email er link e click korle confirmed. Subscription e optional filter policy.
  • Security SQS er moto: in-flight HTTPS, at-rest KMS, client-side. IAM policy + SNS access policy (resource policy): cross-account, S3 event ke topic e likhte dite.
Exam: Email / SMS / mobile app notification, "notify many" → SNS (SQS + Lambda diye SNS banano na). Delivery transport: Email, SMS, SQS, HTTP/S, Lambda; CloudFront / FTP / SNMP na. HR account Finance er topic access → Finance er topic e policy, Principal = HR account (Resource na). Hajar notification e network choke → protibar full snapshot pathao (constant work, course e nai).

Amazon Data Firehose

Shohoj kore: Pipe + tank: data dhoke, dorkar hole Lambda diye bodlay, tank (buffer) bhorle ba time hole S3 / Redshift / OpenSearch e batch e dhele dey. Tai near real-time. No storage, no replay, server nai. Aager naam "Kinesis Data Firehose".

Firehose pipeline

Backup
All ba shudhu failed data→ S3 backup bucket
Common combo
KDSreal-time ingest→ FirehoseLambda transform→ S3 + Redshift

Tin AWS destination mone rakho: S3, Redshift, OpenSearch (purono naam Elasticsearch). EMR na.

  • Fully managed, serverless, automatic scaling, pay for what you use.
  • Input: CSV, JSON, Parquet, Avro, raw text, binary. Convert to Parquet / ORC; compress gzip / snappy. Custom transform (CSV → JSON) = Lambda.
  • Buffer size ba time e flush: default size 5 MB; boro buffer (jemon 128 MB) = efficient, chhoto = druto. Interval 60 s (minimum) theke 900 s; 300 s = 5 min wait.
  • Hands-on: Firehose nijer IAM role banay (KDS porte, S3 e likhte); error log CloudWatch Logs e; Firehose banano-r por pathano data-i jay.
  • Question theke (course e nai): source KDS set thakle oi Firehose e Kinesis Agent shorashori likhte pare na; agent KDS e likhbe. Kinesis consumer result rakhte pare S3, DynamoDB, Redshift e.

Amazon MQ

Shohoj kore: SQS / SNS "cloud-native", AWS er nijer (proprietary) API. On-prem er purono app open protocol e broker er sathe kotha bole. Cloud e ante SQS / SNS er jonno code abar likhte na chaile AWS oi broker-i managed kore dey: Amazon MQ (RabbitMQ ba ActiveMQ).

MQ high availability (us-east-1)
Client→ Broker ACTIVEus-east-1a↔ Amazon EFSshared storage↔ Broker STANDBYus-east-1b, failover

Duita broker ek-i EFS mount kore, tai failover e standby same data pay.

  • Open protocol: MQTT, AMQP, STOMP, Openwire, WSS. Engine: RabbitMQ, ActiveMQ.
  • Ek broker e queue feature (~SQS) ar topic feature (~SNS) duitai.
  • Server e chale, tai SQS / SNS er moto (prai infinite) scale kore na; server issue hote pare, tai HA = Multi-AZ active/standby + failover, backend storage EFS.
Exam: On-prem MQTT / AMQP broker, "migrate without re-engineering / changing code", self-managed RabbitMQ unstable → Amazon MQ. Kubernetes app + AMQP queue, least overhead → EKS + Amazon MQ. Highest availability, least ops: MQ active/standby (2 AZ) + Multi-AZ ASG consumer + RDS Multi-AZ. Trap: SQS AMQP bole na (re-engineer lagbe); nijer EC2 te RabbitMQ chalano beshi kaaj.

Exam traps

  • "Shob notun message delay" dekhle delay queue; "kichu message" dekhle message timer; visibility timeout ba DLQ na.
  • Standard → FIFO dekhle delete + recreate (.fifo), convert na. S3 event FIFO SQS e jay na, Standard e jay.
  • S3 upload, worker fleet er ekta kaj korbe dekhle S3 → SQS, SNS na.
  • SNS subscriber list e Kinesis Data Streams nai; Firehose ache. SNS FIFO topic e shudhu SQS.
  • KDS data ek din por nai dekhle default retention 24 h; retention barao, shard ba KPL na.
  • Hot shard (kom partition key) dekhle key bodlao; shard barano ba on-demand fix kore na.
  • "Near real-time" dekhle Firehose; "real-time + replay" dekhle KDS.
  • EC2 te SQS access dekhle IAM role, EC2 te IAM user key na (on-prem e user key thik).
  • MQ HA dekhle active/standby across 2 AZ, nijer EC2 te RabbitMQ na.

Number mone rakho

  • SQS retention default 4 din, max 14 din; ek receive e max 10 message; latency < 10 ms.
  • SQS message 256 KB (ajke: 1 MiB; slide e 1,024 KB).
  • Visibility timeout default 30 s, range 0 s - 12 h. Long polling 1-20 s. Delay queue / message timer 0-15 min.
  • SQS FIFO 300 msg/s, batch e 3,000 msg/s (ajke: high throughput mode e aro beshi); dedup window 5 min.
  • SNS: 12,500,000 subscription / topic, 100,000 topic; FIFO topic 300 publish/s.
  • KDS shard: in 1 MB/s ba 1,000 rec/s, out 2 MB/s (enhanced fan-out: 2 MB/s per consumer). Retention 1-365 din, default 24 h.
  • KDS on-demand: default 4 MB/s ba 4,000 rec/s, gato 30 din er peak; max 200 MB/s write.
  • KDS record 1 MB (ajke: 10 MiB).
  • Firehose buffer default 5 MB; interval 60 s (min) - 900 s.
