Elastic IP (PDF p. 82-83 (part p. 5-6))

  • EC2 instance stop kore abar start korle tar public IP bodlate pare.
  • Instance er jonno fixed public IP lagle → Elastic IP.
  • Elastic IP = ekta public IPv4 ja tumi own koro, jotokkhon delete na koro.
  • Ek somoy shudhu ek instance e attach kora jay.
  • Kaje lage: instance ba software fail korle, EIP ta druto onno instance e remap kore failure "dhaka" (mask) dewa jay (nijer account er instance e).
  • Account e shudhu 5 ta Elastic IP (AWS ke bole barano jay).

EC2 te default ki thake (PDF p. 84 (part p. 7))

  • Protita EC2 machine pay: private IP (AWS er internal network er jonno) + public IP (WWW er jonno).
  • SSH korar somoy private IP diye hoy na: tumi oi network e nao (VPN thakle alada kotha). Shudhu public IP diye.
  • Machine stop → start korle public IP bodlate pare.
Exam: "Stop/start er por public IPv4 bodle geche, fixed public IPv4 chai" → Elastic IP allocate kore attach. OS er bhitore DHCP theke static kora, AWS Support ke bola, "shudhu private IP fixed kora jay": sob bhul (U06-Q1). "Kon IP shudhu EC2/AWS network er bhitor theke reach kora jay" → Private IP; public ar Elastic IP internet theke (B6-Q23). Trap: "EIP best practice" na; scenario te "highly available / scalable" thakle Load Balancer ba DNS (Route 53) beshi bhalo.

Lecture 3 + 4 (hands-on) · EC2 Placement Groups · PDF p. 85-89 (part p. 8-12)

Placement Group: instance gulo hardware e kivabe boshbe

Shohoj kore (office er udaharon): Cluster = pura team ek table e: kotha druto, kintu table bhangle sobai bipode. Spread = protita boss alada building e: ekta building e agun lagle baki ra thik, kintu building kom (7 ta). Partition = protita team alada floor e (floor = rack): ek floor er current gele shudhu oi team bondho, ar team e onek lok rakha jay.

  • Kokhono kokhono EC2 instance kothay boshbe (placement strategy) sheta nijer control e chao. Ei strategy define kora hoy placement group diye.
  • AWS er hardware e tumi shorashori haat dao na; shudhu AWS ke bolo instance gulo ekta arekta r tulonay kivabe boshbe.
  • Group banate ekta strategy choose koro (PDF p. 85 (part p. 8)):

Cluster (PDF p. 86 (part p. 9))

Cluster placement group: same AZ, pashapashi
EC2⇄ 10 Gbps EC2⇄ low latency EC2
Ek AZ (jemon us-east-1a)

Instance gulor moddhe network khub druto, kintu sob dim ek jhuri te (ek AZ).

  • Pro: Durdanto network: instance gulor moddhe 10 Gbps bandwidth, jodi Enhanced Networking enable thake (recommended). Low latency, high throughput.
  • Con: AZ fail korle shob instance ekshathe fail. Instructor: ei use case e sadharonoto eta mene neya jay.
  • Use case: Big Data job ja druto shesh korte hobe; app jar instance gulor moddhe extremely low latency ar high network throughput lage.

Spread (PDF p. 87 (part p. 10))

3 AZ, 6 EC2, protita alada hardware e

EC2 → Hardware 2 us-east-1bEC2 → Hardware 3
EC2 → Hardware 4 us-east-1cEC2 → Hardware 5

Hardware 1 fail korle Hardware 2 er instance thik thake: us-east-1a er duita instance ekshathe pore na.

  • Cluster er ekdom ulto: lokkho failure risk komano.
  • Pro: Multiple AZ e chhoray; simultaneous failure er risk kom; protita EC2 alada physical hardware e.
  • Con: 7 instance per AZ per placement group. Tai app "bhalo size er, kintu khub boro na" hote hobe. Instructor duibar bolechen "remember".
  • Use case: App jar high availability maximize korte hobe; critical app jekhane protita instance er failure onno gulo theke alada thakte hobe.

Partition (PDF p. 88 (part p. 11))

Partition = rack. Protita partition e onek EC2
us-east-1aPartition 1 (rack): EC2 ×4
Partition 2 (rack): EC2 ×4 us-east-1bPartition 3 (rack): EC2 ×4

Partition 2 er rack gele shudhu tar 4 ta instance jay; Partition 1 ar 3 thik thake.

  • Ek AZ te max 7 partition; partition gulo same region er multiple AZ e thakte pare.
  • Protita partition = AWS er ekta rack. Ek partition er instance onno partition er instance er sathe rack share kore na → rack failure theke alada.
  • Ek partition fail korle tar onek EC2 jete pare, kintu onno partition e prabhab nai.
  • Hundreds of EC2 porjonto: Spread theke eta-i boro parthokko (Spread = 7 per AZ).
  • Kon instance kon partition e: EC2 eta metadata (instance metadata service) theke jante pare.
  • Use case: app nije partition aware (data ar server partition jure bhag kore): HDFS, HBase, Cassandra, Apache Kafka (big data).

Precision time (PDF p. 89 (part p. 12))

  • Slide e notun add hoyeche; lecture video te nai.
  • Instance gulo emon hardware e boshe jar high-precision time source e direct access ache.
  • Enhanced Amazon Time Sync Service: standard NTP er cheye beshi accurate.
  • PTP Hardware Clock + hardware packet timestamping (shudhu Linux).
  • Use case: distributed database, financial timestamping, event ordering.

"Course er por ki bodlalo" dekho: AWS docs e eta 4 nombor strategy, ar eta ke cluster group er "parent" kora jay.

Hands-on: kothay ki (Lecture 4)

  1. EC2 console → left menu Network & Security → Placement Groups → Create placement group.
  2. my-high-performance-group → strategy Cluster (instance kachakachi, maximum network).
  3. my-critical-group → strategy Spread. Spread level: rack (default, eta-i jante hobe) ba host (shudhu AWS Outposts er jonno).
  4. my-distributed-group → strategy Partition; partition shonkhya 1 theke 7 (demo te 4).
  5. Instance launch → ekdom niche Advanced details → Placement group name e group select.
Exam: Keyword dekhe strategy:
  • "Highest network performance between instances", "low network latency compute cluster", "HPC", "big data, performance chai" → Cluster (U06-Q2, B3-Q42, S1-Q23, S4-Q20). Trap: Spot, User Data kernel tuning, Dedicated Instance, Direct Connect, private subnet, multi-AZ: kono tai network latency komay na.
  • "Critical app, maximum availability, AZ failure", "instance gulo ekshathe fail jeno na kore", alpo kichu instance → Spread (U06-Q3).
  • "Hadoop / HDFS / HBase / Cassandra / Kafka", "50 instance per AZ", "large distributed and replicated workload, correlated hardware failure komao" → Partition (S2-Q12, S6-Q40). Spread na: 7 er beshi hoy na. Cluster na: ek AZ, HA nai.
  • "Multi-AZ placement group" bole kichu nai (S6-Q40 er distractor). "Auto Scaling group" placement group na (S1-Q23).

Subtitle e "available T-zones" = Availability Zones, "my-distributor-group" = my-distributed-group; thik kore likhechi.

Lecture 5 · Elastic Network Interfaces (ENI) - Overview · PDF p. 90 (part p. 13)

ENI: EC2 er virtual network card

Shohoj kore: ENI holo phone er SIM card. Phone (EC2) e SIM dhokale number (private IP) pay. Phone noshto hole SIM khule onno phone e dhokale number same thake, lok ager number e-i call kore. Shorto: SIM shudhu oi elakar (AZ er) phone e chole.

  • ENI = Elastic Network Interface: VPC er logical component, ekta virtual network card.
  • ENI-i EC2 instance ke network access dey. EC2 er baire-o ENI use hoy (course e pore dekhbe).
  • Protita EC2 te eth0 = primary ENI thake: network connectivity ar private IP dey.
  • Chaile secondary ENI (eth1) add kora jay: aro ekta private IPv4 pabe.

Ekta ENI te ki ki thakte pare (PDF p. 90 (part p. 13))

Duita mul kotha

  • ENI EC2 theke alada kore create kora jay, tarpor on the fly attach ba ek instance theke arek instance e move kora jay → failover.
  • ENI ekta specific AZ e bandha. Je AZ e banabe, shudhu oi AZ er instance e attach hobe.

Exam: "ENI onno AZ er instance e attach kora jay" → False (U06-Q4). "Static private IP, druto network failover onno instance e" → secondary ENI move. Private IP ENI er sathe thake, tai VPC te stop/start e private IP bodlay na (B4-Q41). ENI te ek ba ekadhik security group attach hoy (slide).

ENI attach er 3 naam (B2-Q32): hot attach = instance running, warm attach = instance stopped, cold attach = instance launch er somoy. Secondary ENI detach kora jay (running ba stopped), kintu primary ENI (eth0) detach kora jay na. Source: Network interface attachments. amar jana, course e nai

Subtitle e ENI te "one or more public IPv4" bola; slide e "One Public IPv4", slide er ta niyechi.

Lecture 8 + 9 (hands-on) · EC2 Hibernate · PDF p. 91-93 (part p. 14-16)

EC2 Hibernate: RAM shoho instance ke ghum parano

Shohoj kore: Laptop shut down korle abar on korte boot hoy, sob app abar khulte hoy. Laptop er lid bondho (hibernate) korle khulle sob tab, sob kaj thik jekhane chilo shekhane. EC2 Hibernate = lid bondho kora: RAM er sob kichu disk e likhe rakhe, start e abar RAM e tule dey.

Age ja jani: stop, terminate, start (PDF p. 91 (part p. 14))

KajKi hoy
StopDisk (EBS) er data thik thake, porer start e paoa jay
TerminateJe EBS volume (root) "destroy" hote set kora, sheta harabe; baki volume theke jay
Prothom startOS boot hoy + EC2 User Data script chale
Porer start guloOS boot hoy
TarporApp start hoy, cache warm up hoy: eta somoy ney!

Hibernate ki dey (PDF p. 92 (part p. 15))

  • In-memory (RAM) state preserve hoy.
  • Instance boot onek druto: OS stop ba restart hoy na, shudhu "frozen" thake.
  • Bhitore: RAM er state root EBS volume er ekta file e likha hoy.
  • Tai root EBS volume encrypted hote hobe, ar RAM dhorar moto jayga thakte hobe.
Hibernate er dhap (PDF p. 92 (part p. 15))
RunningRAM e data→ Hibernate StoppingRAM dump → root EBS (encrypted)→ Shutdown StoppedRAM khali, dump EBS e→ Start RunningEBS theke RAM e load

Start er por instance mone kore se kokhono stop-i hoy ni.

Use case (PDF p. 92 (part p. 15))

  • Long-running processing: process kokhono bondho korte chao na.
  • RAM state save rakha.
  • Je service initialize hote onek somoy ney: abar initialize na kore chalu rakhte chao.

Hands-on (Lecture 9)

  1. Launch instance (Amazon Linux 2, t2.micro, SG launch-wizard-1).
  2. Advanced details → Stop - Hibernate behavior → Enable. Warning: root volume e RAM er jayga lagbe ar root EBS encrypted hote hobe.
  3. Storage → Advanced → root EBS volume Encrypted, KMS key default aws/ebs.
  4. Size check: root 8 GB, t2.micro er RAM 1 GB → RAM disk e dhorbe, thik ache.
  5. EC2 Instance Connect diye dhuke uptime: prothome 0 min, pore 1 min (shesh restart theke koto khon chalu).
  6. Instance state → Hibernate instance: RAM er data EBS e likhe instance stopped hoy. Tarpor Start.
  7. Abar uptime: 0 theke shuru hoy na, 2 min dekhay. Normal stop/start hole 0 theke shuru hoto. Mane OS er dik theke instance kokhono stop hoy ni.
  8. Shesh e instance terminate.
Exam: "RAM / in-memory state rakhte chai", "boot druto, app/cache abar warm up korte chai na", "service initialize hote onek somoy" → EC2 Hibernate (normal stop e RAM harabe). Hibernate er shorto: root = encrypted EBS, instance store na → "root volume must be Instance Store" bhul statement (U06-Q5). RAM < 150 GB, On-Demand / Reserved / Spot support: thik. Demo te hibernate launch er somoy enable korechi.

AWS docs theke (Hibernation prerequisites, How hibernation works): hibernation shudhu launch e enable kora jay, existing instance e na. Hibernate er por start e public IPv4 notun hoy (stop er moto), private IPv4 ar Elastic IP thake. Instance store er data harabe. Auto Scaling group ba ECS er instance hibernate kora jay na. Windows e RAM 16 GiB porjonto. amar jana, course e nai

Subtitle e "stop hibernate behavior" console er "Stop - Hibernate behavior" setting; ar "specific star behavior" bujha jay na (mone hoy "stop behavior"), bad diyechi.

Aajker kotha: EC2-Classic puropuri retire hoye geche (2022-2023), ekhon sob instance VPC te. Tai A/D er EC2-Classic statement ekhon ar relevant na.

Why the other options are wrong

Keyword: incorrect + VPC private IP on stop → C (VPC te private IP stop/start e thake)

Original explanation (English)

For EC2 instances launched in EC2-Classic, AWS releases the private IPv4 address when the instance is stopped or terminated. If you restart your stopped instance, it receives a new private IPv4 address.

For EC2 instances launched in a VPC, a private IPv4 address remains associated with the network interface when the instance is stopped and restarted. It is only released when the instance is terminated.
