4·1S1-Q31Stephane set 1 · Q31Design Secure Applications and Architectures

An IT consultant is helping the owner of a medium sized business setup an AWS account. What are the security recommendations he must follow while creating the AWS account root user? (Select 2)

একজন IT consultant একটি মাঝারি আকারের business-এর মালিককে একটি AWS account setup করতে সাহায্য করছেন। AWS account root user তৈরি করার সময় তাকে কোন security recommendation-গুলো মানতে হবে? (2টি বেছে নিন) (Select 2)

Choose 2 answers

Correct: A, E. Why it is right

Root user protect korar best practice:

  • Strong password dao (password policy er moto strong).
  • MFA enable koro - password leak holeo device chara login hobe na (PDF p. 30).

Root shudhu account setup er jonno, kokhono share na (PDF p. 39).

Why the other options are wrong

  • B. Root access key thakai uchit na; thakle delete koro. Encrypt kore S3 te rakha recommendation na.
  • C. Root access key create na kora-i best; ar kauke share kora to ekdom na.
  • D. Root username/password email e pathano mane credential share - best practice er ulta.

Keyword: root user security recommendations (Select 2) → strong password + MFA

Original explanation (English)

Here are some of the best practices while creating an AWS account root user: 1) Use a strong password to help protect account-level access to the AWS Management Console. 2) Never share your AWS account root user password or access keys with anyone. 3) If you do have an access key for your AWS account root user, delete it. If you must keep it, rotate (change) the access key regularly. You should not encrypt the access keys and save them on Amazon S3. 4) If you don't already have an access key for your AWS account root user, don't create one unless you absolutely need to. 5) Enable AWS multi-factor authentication (MFA) on your AWS account root user account.

Reference: https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html#create-iam-users

4·2S5-Q34Stephane set 5 · Q34Design Secure Applications and Architectures⚠ outdated

You are working as an Engineering Manager at a company and you manage several development teams and monitor their access across multiple accounts. To get the teams up and running quickly, you had initially created multiple roles with broad permissions that are based on job function in the development accounts. Now, the developers are ready to deploy workloads to production accounts and you only want to grant them minimum possible permissions that the developers would actually need.

Which of the following is the best way of implementing this requirement?

আপনি একটি company-তে Engineering Manager হিসেবে কাজ করছেন এবং কয়েকটি development team manage করেন ও একাধিক account জুড়ে তাদের access monitor করেন। team-গুলোকে দ্রুত কাজ শুরু করাতে আপনি শুরুতে development account-গুলোতে job function অনুযায়ী broad permission-সহ একাধিক role তৈরি করেছিলেন। এখন developer-রা production account-এ workload deploy করতে প্রস্তুত, এবং আপনি তাদের শুধু সেই ন্যূনতম সম্ভাব্য permission দিতে চান যা developer-দের আসলে দরকার হবে।

এই requirement implement করার সবচেয়ে ভালো উপায় নিচের কোনটি?

⚠ Outdated: Explanation bole 'action last accessed' shudhu S3 er jonno - eta ar thik na; ekhon EC2, Lambda, IAM soho 100+ service e action-level last accessed info dey. Tobe roles (D) ei best answer, groups (C) na. source

Correct: D. Why it is right

IAM Access Advisor dekhay kon service er permission deya ache ar last accessed kobe (PDF p. 38). Shei data diye production er jonno shudhu used permission diye new IAM roles banao, baki revert koro = least privilege.

Multi-account e developer ra role diye access kore, tai role-i thik. Ajker kotha: action last accessed shudhu S3 er jonno na, ekhon EC2, Lambda, IAM soho 100+ service e pawa jay.

Why the other options are wrong

  • A. Kaj korbe, kintu guess kore permission diye pore missing gulo add kora slow ar bar bar follow-up lage; data-driven na.
  • B. Service account application er programmatic access er jonno; developer der minimum permission thik korar sathe somporko nai.
  • C. Access Advisor data thik ache, kintu IAM Groups ekta account er bhitore thake ar account-er baire use hoy na; multi-account e developer der role diye access dite hoy.

Keyword: minimum possible permissions + multiple accounts + already roles → Access Advisor + new IAM roles

Original explanation (English)

Correct option:

Use Access Advisor to determine the permissions the developers have used in the last few months and only give those permissions (with new IAM roles) while reverting the rest

Access advisor will determine the permissions your developers have used by analyzing the last timestamp when an IAM entity (for example, a user, role, or group) accessed an AWS service. This information helps you audit service access, remove unnecessary permissions, and set appropriate permissions across different environments (To view the last accessed information in the AWS Management Console, you must have a policy that grants the necessary permissions).

For example, you can grant broad access to services in development accounts and then reduce permissions for access to specific services in production accounts. Finally, as you manage more IAM entities and AWS accounts, you need a way to scale these processes through automation. To help you achieve this automation, you can now use IAM access advisor APIs with the AWS Command Line Interface (AWS CLI) or a programmatic client.

Incorrect options:

Create IAM Roles with limited permissions for each of the teams. Any missing permissions can be added to these roles if developers face issues in accessing services they need - This is a possible option but not an optimized one. For an organization spread across countries and holding multiple AWS accounts, this exercise will not only take a lot of time, but it will also need daily follow-ups to make sure all teams have necessary permissions.

Create service accounts for each of the teams and restrict the associated policy to only the permissions needed for the particular functionality - Service account is an account used for programmatic access by applications running outside of the AWS environment. This has no bearing on the current use case.

Use Access Advisor to know the action last accessed information for the last few months and create IAM Groups with the permissions gained from these insights - Action last accessed information is only relevant for Amazon S3 management actions, whereas the given use-case caters to access details for all the services used by the user, not just Amazon S3.

https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_access-advisor.html
