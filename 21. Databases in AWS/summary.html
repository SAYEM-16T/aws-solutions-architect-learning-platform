Big picture

Shohoj kore: Kapor almari te, boi bookshelf e, taka locker e. Shob ek almari te rakha jay, kintu kaaj kothin. Prothome dekho data er shape ar kivabe query hobe, tarpor constraint ("serverless", "no capacity planning", "no code change", "least overhead").

Amazon RDS

Shohoj kore: Chena PostgreSQL / MySQL, kintu patch, backup, failover AWS kore. Instance size ar EBS volume type + size tumi age thik koro, tai provisioned, serverless na.

HA vs read scaling

Analytics / reporting→ Read Replicaread scale
Backup
Automated backup35 din→ PITR →Notun DB Manual snapshotlong-term

Production DB te analytics chalale Read Replica; Multi-AZ standby te query kora jay na.

PointDetail
EnginePostgreSQL, MySQL, Oracle, SQL Server, DB2, MariaDB, Custom

SecurityIAM, Security Group (network), KMS (at rest), SSL / TLS (in transit); username / password ba IAM authentication (RDS Proxy diye enforce), Secrets Manager e credential

Exam: "Relational, SQL, transactions (insert / update / delete)" → RDS. Trap: DocumentDB / DynamoDB NoSQL, ElastiCache cache (SQL nai). RDS e built-in replica auto-scaling nai, Read Replica / Multi-AZ nije banate hoy.

Amazon Aurora

Shohoj kore: Aurora te storage ar compute alada. Disk ta ekta shared layer: data 6 copy, 3 AZ (bodlano jay na), nije sare (self-healing), nije bare. Upore writer ar reader instance shei ek storage pore, tai replica, failover, clone shob druto.

Aurora cluster

DB instancescluster, multi-AZ↓ Shared storage6 copy × 3 AZ, self-healing, auto-grow
Aurora Global
Primary regionread + write→ < 1 s storage replication → Secondary region16 read instance; problem hole promote

Cluster bole kothay likhbe / porbe janate writer ar reader endpoint lage.

FeatureKokhon
PostgreSQL / MySQL compatible APIRDS er use case, kintu kom maintenance, beshi flexibility, performance, feature
Security / monitoring / maintenanceRDS er moto; backup + restore option jante hobe (Section 09)

Aurora GlobalCross-region: region proti 16 DB read instance, storage replication < 1 second; secondary ke primary promote
Aurora Machine LearningAurora data e SageMaker, Comprehend diye ML

Course e nai (question theke): Aurora PostgreSQL e AI feature er jonno vector storage lagle pgvector extension install koro: same DB te vector table, notun service er khoroch nai.

Exam: "OLTP + built-in auto-scaling + maximum storage replica" → Aurora (RDS na). "OLTP + unpredictable spike, age jana nai" → Aurora Serverless; DynamoDB on-demand spike nibe kintu NoSQL, OLTP relational proshne bhul. Vector store + Aurora PostgreSQL already ache + cheapest → pgvector, notun OpenSearch / DocumentDB / Neptune ML cluster na.

Amazon ElastiCache

Shohoj kore: Bar bar library (DB) te na giye dorkari kotha pocket notebook (RAM) e likhe rakho: sub-millisecond read. Kintu notebook dekhar obbhash (app code) tomakei likhte hobe. RDS er moto offering, tobe cache er jonno.

Cache on top of RDS
Appcode change kore cache logic→ ElastiCachehit: sub-ms→ miss → RDS / Aurora
Web app→ElastiCacheuser session data

"Code change chara cache" chaile ElastiCache bhul answer.

PointDetail

CapacityInstance type select (jemon cache.m6g.large), provisioned
HA / scaleRedis: clustering, Multi-AZ, Read Replica (sharding)

Exam: "Redis / Memcached API", "in-memory", "session store", "sub-ms" → ElastiCache. RDS (JDBC), DynamoDB (nijer API), OpenSearch (HTTP) Redis-compatible na. Trap: "caching without code change" → ElastiCache na; DynamoDB hole DAX. Boro file durable rakhte ElastiCache na (durable na).

Amazon DocumentDB

Shohoj kore: Aurora jemon PostgreSQL / MySQL er AWS-implementation, DocumentDB temni MongoDB er. MongoDB = NoSQL, JSON data store, query, index kore. Driver / code same rekhe DB ta AWS ke manage korte dao.

Analogy
PostgreSQL / MySQL→ AWS version →Aurora
MongoDB (JSON)→ AWS version →DocumentDB
On-prem Kubernetes + MongoDB → AWS, kono change chara
Kubernetes→EKS + Fargatenode manage nai MongoDB→DocumentDB

Aurora er moto "deployment concept": cluster, 3 AZ replication, storage auto-grow.

  • Fully managed, highly available, 3 AZ e replication.
  • Storage nije bare 10 GB increment e; millions of requests per second workload porjonto scale.
Exam: "MongoDB", "JSON documents", "migrate without code change" → DocumentDB. "NoSQL" dekhle DocumentDB ar DynamoDB dutoi bhabo. Trap: "RDS for MongoDB" bole kichu nai; DynamoDB / ECS e code ba deployment change lage, MongoDB on EC2 te overhead.

Amazon Neptune + Neptune Streams

Shohoj kore: Social network: user er friend, post e comment, comment e user er like, user post share kore. Shob ek arekta r sathe jora (vertex + edge) = graph. "Mike er friend der post e mot koto like?" table-join e kothin ar slow, graph DB te shohoj.

Graph
User Mike→ friend → User Ana→ posted → Post← likes ← Users
Neptune Streams
App writes→ Neptune cluster→ Neptune Streamsordered, no duplicate→ HTTP GET (Streams API) → Streams reader app→ S3 / OpenSearch / ElastiCache / onno region er Neptune

Relationship-i data; onek hop (5 level mutual connection) e Neptune fast, SQL join slow.

PointDetail
KiFully managed graph database, highly connected dataset er complex query er jonno optimized
HA3 AZ, 15 read replica porjonto
ScaleBillions of relations, query milliseconds e
Use caseKnowledge graph (Wikipedia), fraud detection, recommendation engine, social networking

Streams useChange hole notification; onno data store (S3, OpenSearch, ElastiCache) sync; region er moddhe Neptune replicate

Question theke: Neptune data rakhe vertex + edge hisabe; query language er ekta SPARQL (DynamoDB er PartiQL).

Exam: "Friends, likes, highly connected, mutual connections up to 5 levels, many-to-many", "IT infrastructure map + security risk query" → Neptune. Change monitor + relationship analyze + recommendation → Neptune + Neptune Streams (least overhead; Kinesis Neptune er change shorashori pore na). Trap: RDS / Aurora / Athena multi-level JOIN "kaaj korbe" kintu slow; OpenSearch search, Redshift OLAP, QLDB ledger, QuickSight shudhu visualize.

Shohoj kore: Apache Cassandra open-source distributed NoSQL; nije chalano kothin. Keyspaces e ek-i CQL (Cassandra Query Language), kintu serverless: traffic onujayi table nije bare kome.

Amazon QLDB (Quantum Ledger Database)

Shohoj kore: Ledger = financial transaction er khata (bank passbook). Entry ekbar likhle muche fela ba bodlano jay na (immutable). Bhitore ekta journal: protita modification e cryptographic hash hishab hoy, tai je keu verify korte pare kichu delete / modify hoy ni.

Append-only journal
Change 1hash→ Change 2hash→ Change 3hash→ Verifykichu muche jay ni
Central vs decentralized
QLDBcentral authority (Amazon), financial regulation er sathe mile Managed Blockchaindecentralized, onek party

Application data er puro change history review kora jay.

  • Fully managed, serverless, HA, 3 AZ replication.
  • Common ledger blockchain framework er cheye 2-3x better performance; data SQL diye manipulate.
Exam: "Financial / accounting records, credit-debit, immutable, cryptographically verifiable log of changes" → QLDB. Trap: Aurora, Neptune, Redshift, Timestream, DocumentDB verifiable history dey na. Decentralized → Managed Blockchain. (Ajke QLDB end of support, kintu exam answer QLDB.)

Shohoj kore: Time series = time shoho point er series ("10:00 e 31°C, 10:01 e 31.5°C"). Relational DB te eta slow + dami; Timestream eta-r jonno banano: recent data memory te, purono data cost-optimized storage e.

Exam traps

  • "Caching without code change" dekhle DynamoDB hole DAX, ElastiCache na (ElastiCache e app code bodlate hoy).
  • "NoSQL" dekhle DynamoDB ar DocumentDB dutoi bhabo; engine er naam (MongoDB / Cassandra) thakle sheta-i decide kore.
  • "Serverless NoSQL + global" dekhle course answer DynamoDB, DocumentDB na.
  • Analytics production DB slow korche dekhle Read Replica, Multi-AZ na (standby te query hoy na).
  • "OLTP" dekhle relational (RDS / Aurora); Redshift (OLAP) ba DynamoDB na.
  • Onek level er relationship dekhle Neptune; SQL JOIN "kaaj korbe" kintu best na.
  • Decentralized dekhle Managed Blockchain, QLDB na (QLDB central).
  • Smooth gradual load → DynamoDB provisioned + auto scaling; hothat steep spike → on-demand.
  • Serverless: DynamoDB, S3, Keyspaces, QLDB, Timestream, Aurora Serverless. Provisioned: RDS, ElastiCache (instance type), Aurora cluster.
  • DynamoDB PITR restore, on-demand backup restore, S3 import: shob notun table e.

Number mone rakho

  • Backup / PITR 35 din: RDS, DynamoDB, Keyspaces.
  • Aurora storage 6 copy, 3 AZ; Aurora Global replication < 1 s, region proti 16 read instance.
  • Latency: ElastiCache sub-ms, DynamoDB ms, DAX microsecond, Keyspaces single-digit ms, Neptune query ms.
  • DynamoDB item max 400 KB (choto document 100s KB); Kinesis Data Streams retention 1 bochor porjonto.
  • S3 max object: slide 50 TB (video 5 TB bole; purono question e 5 TB).
  • Neptune 3 AZ, 15 read replica, billions relation; DocumentDB storage 10 GB kore bare, 3 AZ; Keyspaces 3 copy; QLDB 3 AZ.
  • Timestream relational er cheye 1000s times fast, 1/10th cost, trillions event / din; QLDB blockchain framework er cheye 2-3x fast.
  • QLDB exam answer (ajke: end of support 31 July 2025). Timestream (ajke: LiveAnalytics notun customer nay, Timestream for InfluxDB ache). DocumentDB (ajke: Serverless ar Global Clusters ache, kintu course key DynamoDB).
