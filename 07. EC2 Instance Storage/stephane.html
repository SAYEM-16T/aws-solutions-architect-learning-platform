7·1S1-Q41Stephane set 1 · Q41Design High-Performing Architectures

The solo founder at a tech startup has just created a brand new AWS account. The founder has provisioned an EC2 instance 1A which is running in region A. Later, he takes a snapshot of the instance 1A and then creates a new AMI in region A from this snapshot. This AMI is then copied into another region B. The founder provisions an instance 1B in region B using this new AMI in region B. At this point in time, what entities exist in region B?

একটি tech startup-এর একক founder সবেমাত্র একটি একদম নতুন AWS account তৈরি করেছেন। founder একটি EC2 instance 1A provision করেছেন, যা region A-তে চলছে। পরে তিনি instance 1A-এর একটি snapshot নেন এবং তারপর এই snapshot থেকে region A-তে একটি নতুন AMI তৈরি করেন। এরপর এই AMI অন্য একটি region B-তে copy করা হয়। founder region B-তে এই নতুন AMI ব্যবহার করে region B-তে একটি instance 1B provision করেন। এই মুহূর্তে region B-তে কোন entity-গুলো আছে?

Correct: A. Why it is right

AMI build korle pichone EBS snapshot toiri hoy (PDF p. 102). EBS-backed AMI onno Region e copy korle tar backing snapshot-o destination Region e copy hoy. Tarpor oi AMI theke instance launch.

Tai Region B te: 1 AMI + 1 snapshot + 1 EC2 instance.

Why the other options are wrong

  • B. AMI copy er sathe tar snapshot-o Region B te ashe; snapshot ta baad porche.
  • C. Copied AMI-o Region B te ache (oi AMI theke-i launch); AMI baad porche.
  • D. Region B te AMI ekta-i (copy kora ta); 2 ta AMI hoy na.

Keyword: AMI copied to region B + instance launched → 1 AMI + 1 snapshot + 1 instance

Original explanation (English)

When the new AMI is copied from region A into region B, it automatically creates a snapshot in region B because AMIs are based on the underlying snapshots. Further, an instance is created from this AMI in region B. Hence, we have 1 EC2 instance, 1 AMI and 1 snapshot in region B.

7·2S1-Q43Stephane set 1 · Q43Design High-Performing Architectures⚠ key doubtful

A research group at an ivy-league university needs a fleet of EC2 instances operating in a fault-tolerant architecture for a specialized task that must deliver high random I/O performance. Each instance in the fleet would have access to a dataset that is replicated across the instances. Because of the resilient architecture, the specialized task would continue to be processed even if any of the instances goes down. Which of the following options is the MOST cost optimal and resource efficient solution to build this fleet of EC2 instances?

একটি ivy-league university-র একটি research group-এর একটি বিশেষ task-এর জন্য fault-tolerant architecture-এ চলা EC2 instance-এর একটি fleet দরকার, যাকে high random I/O performance দিতে হবে। fleet-এর প্রতিটি instance-এর একটি dataset-এ access থাকবে, যা instance-গুলো জুড়ে replicate করা। resilient architecture-এর কারণে, কোনো instance down হয়ে গেলেও বিশেষ task-টি process হতে থাকবে। EC2 instance-এর এই fleet তৈরি করার জন্য নিচের কোন option সবচেয়ে cost optimal (MOST cost optimal) এবং resource efficient solution?

⚠ Answer key doubtful. Key says: B; verified answer: C. Key e B (EFS) deya, kintu original explanation nijei bole Instance Store (C) best. AWS doc bole instance store 'temporary data that you replicate across a fleet of instances' er jonno ideal, eta instance er dam er moddhei included, ar high random I/O dey. EFS network storage, extra khoroch. Tai thik answer C. Link: https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/InstanceStorage.html

Correct: B. Why it is right

Answer key B (EFS) dey, kintu eta mis-key mone hoy. Original explanation nijei Instance Store (C) er pokkhe: high random I/O lage, dataset fleet e replicate kora, ar fault-tolerant tai ek instance gele problem nai.

Instance store = host er physical disk, sobcheye beshi I/O, ar storage instance er dam er moddhei (PDF p. 103). AWS docs: fleet jure replicate kora temporary data er jonno ideal. EFS network storage, alada khoroch. Tai MOST cost optimal = C.

Why the other options are wrong

  • A. EBS e high random I/O pete io1 (Provisioned IOPS) lagto, khoroch onek bare; instance store er storage instance er dam er moddhe.
  • C. Asole eta-i thik answer: high random I/O, instance er dame included, ar replicated data ek instance e harale problem nai. Key ta bhul.
  • D. S3 object storage, local disk na; high random I/O ar local access dite pare na.

Keyword: high random I/O + dataset replicated + MOST cost optimal → Instance Store (key B bhul)

Original explanation (English)

An instance store provides temporary block-level storage for your instance. This storage is located on disks that are physically attached to the host computer. Instance store is ideal for temporary storage of information that changes frequently, such as buffers, caches, scratch data, and other temporary content, or for data that is replicated across a fleet of instances, such as a load-balanced pool of web servers. Instance store volumes are included as part of the instance's usage cost. Some instance types use NVMe or SATA-based solid state drives (SSD) to deliver high random I/O performance. This is a good option when you need storage with very low latency, but you don't need the data to persist when the instance terminates. As Instance Store based volumes provide high random I/O performance at low cost (as the storage is part of the instance's usage cost) and the fault-tolerant architecture can adjust for the loss of any instance, therefore you should use Instance Store based EC2 instances for this task. EBS based volumes would need to use Provisioned IOPS (io1) as the storage type and that would increase the costs significantly. Using EFS implies that extra resources would have to be provisioned, which is not really required as per the given scenario. EC2 instances with access to S3 based storage would not be able to provide high random I/O as well as local access to replicated dataset. There is no such thing as an S3 based EC2 instance and this option is just added as a distractor.

Reference: https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/InstanceStorage.html

7·5S2-Q23Stephane set 2 · Q23Design High-Performing Architectures

A silicon valley based startup is planning to move its infrastructure to AWS Cloud. The engineering team is running some Proof-of-Concepts to move their business to AWS Cloud. The team wants to store business critical data on Elastic Block Storage (EBS) volumes which provide persistent storage independent of EC2 instances. During one such run, the team found out that on terminating an Amazon EC2 instance, the attached Elastic Block Storage (EBS) volume was also lost, which was contrary to their assumptions. As a solutions architect, could you explain this issue?

Silicon Valley-ভিত্তিক একটি startup তার infrastructure AWS Cloud-এ সরানোর পরিকল্পনা করছে। engineering team তাদের business AWS Cloud-এ সরাতে কিছু Proof-of-Concept চালাচ্ছে। team business critical data Elastic Block Storage (EBS) volume-এ store করতে চায়, যেগুলো EC2 instance থেকে স্বাধীন persistent storage দেয়। এমন একটি run-এর সময় team দেখল যে একটি Amazon EC2 instance terminate করলে attached Elastic Block Storage (EBS) volume-ও হারিয়ে যায়, যা তাদের ধারণার বিপরীত। একজন solutions architect হিসেবে, আপনি কি এই সমস্যাটি ব্যাখ্যা করতে পারেন?

Correct: D. Why it is right

Volume ta chilo instance er root volume. Root EBS er Delete on Termination default enabled, tai instance terminate e root volume-o delete hoy (PDF p. 98). Extra attached volume default e thake.

Root rakhte chaile DeleteOnTermination false koro.

Why the other options are wrong

  • A. EBS data rakhte S3 backup lage na; volume delete hoyeche Delete on Termination er jonno.
  • B. EFS e backup na rakhar karone volume delete hoy na; EBS nijei persistent.
  • C. Bhul: 'always' na. Shudhu Delete on Termination enabled thakle (default e root) delete hoy; extra volume default e thake.

Keyword: terminating instance → attached EBS lost → root volume, Delete on Termination default on

Original explanation (English)

Amazon Elastic Block Store (EBS) is an easy to use, high performance block storage service designed for use with Amazon Elastic Compute Cloud (EC2) for both throughput and transaction intensive workloads at any scale. When you launch an instance, the root device volume contains the image used to boot the instance. You can choose between AMIs backed by Amazon EC2 instance store and AMIs backed by Amazon EBS. Amazon recommends that you use AMIs backed by Amazon EBS, because they launch faster and use persistent storage.

EBS volumes do not need to backup the data on Amazon S3 or EFS filesystem. These options are added as distractors.

By default, the root volume for an AMI backed by Amazon EBS is deleted when the instance terminates. You can change the default behavior to ensure that the volume persists after the instance terminates. Non root EBS volumes remain available even after you terminate an instance to which the volumes were attached.

7·7S2-Q51Stephane set 2 · Q51

You have deployed an application behind a Network Load Balancer, and a target group that groups EC2 instances. The application takes about 3 minutes to start once the system dependencies are installed, and you would like to minimize that time. How should you proceed?

আপনি একটি Network Load Balancer এবং EC2 instance-গুলোকে group করে এমন একটি target group-এর পেছনে একটি application deploy করেছেন। আপনি target group-এ EC2 instance-গুলোর registration এবং de-registration নিজে manage করার সিদ্ধান্ত নিয়েছেন, এবং server-এর সংখ্যা dynamically scale করতে চান। system dependency install হওয়ার পরে application start হতে প্রায় 3 মিনিট লাগে, এবং আপনি সেই সময় minimize করতে চান। আপনার কীভাবে এগোনো উচিত?

Correct: A. Why it is right

Dependencies install er porei app start e 3 minute lage. EC2 Hibernate e RAM state root EBS e save hoy (PDF p. 92): instance age launch kore app chalu kore hibernate rakho. Start korle app already running obosthay resume, 3 minute bache.

Course er use case: 'services that take time to initialize'.

Why the other options are wrong

  • B. User Data shudhu first boot e command chalay (PDF p. 44); app start er time komay na.
  • C. Meta-data shudhu instance er info (IP, instance ID...) dey; speed bare na.
  • D. AMI dependencies age theke install rakhe, kintu app start er 3 minute tobu lagbe; AMI RAM state rakhe na.

Keyword: application takes 3 minutes to start → Hibernate (RAM state rakhe)

Original explanation (English)

Here, the problem is that the application takes 3 minutes to launch, no matter what. EC2 user data won't help us because it's just here to help us execute a list of commands, not speed them up.

The EC2 meta-data is a distractor and can only help us determine some metadata attributes on our EC2 instances.

Creating an AMI may help with all the system dependencies, but it won't help us with speeding up the application start time.

By pre-launching an instance, starting the application, and then using EC2 hibernate, we have the capability to resume it at any point of time, with the application already launched, thus helping us cut the 3 minutes start time.

7·9S3-Q27Stephane set 3 · Q27Design High-Performing Architectures

A big data analytics company is working on a real-time vehicle tracking solution. The data processing workflow involves both I/O intensive and throughput intensive database workloads. The development team needs to store this real-time data in a NoSQL database hosted on an EC2 instance and needs to support up to 25,000 IOPS per volume. একটি big data analytics company একটি real-time vehicle tracking solution নিয়ে কাজ করছে। data processing workflow-তে I/O intensive এবং throughput intensive দুই ধরনের database workload-ই আছে। development team-কে এই real-time data একটি EC2 instance-এ hosted একটি NoSQL database-এ store করতে হবে এবং প্রতি volume-এ 25,000 IOPS পর্যন্ত support করতে হবে। একজন solutions architect হিসেবে, এই use-case-এর জন্য আপনি নিচের কোন EBS volume type recommend করবেন?

Correct: C. Why it is right

25,000 IOPS per volume lage. gp2 er max 16,000 IOPS (PDF p. 106), tai cholbe na. io1 e max 64,000 (Nitro) porjonto provision kora jay (PDF p. 107), ar DB er moto I/O intensive workload er jonno-i banano.

Note: aajke gp3 80,000 IOPS porjonto jay (Sept 2025), kintu option e gp3 nai.

Why the other options are wrong

  • A. gp2 max 16,000 IOPS; 25,000 er kom.
  • B. sc1 Cold HDD, max 250 IOPS; kom access hoy emon data er jonno.
  • D. st1 HDD throughput er jonno, max 500 IOPS; 25,000 IOPS dite pare na.

Keyword: 25,000 IOPS per volume + NoSQL DB → io1 (gp2 max 16,000)

Original explanation (English)

Correct option: "Provisioned IOPS SSD (io1)"

Provisioned IOPS SSD (io1) is backed by solid-state drives (SSDs) and is a high-performance EBS storage option designed for critical, I/O intensive database and application workloads, as well as throughput-intensive database workloads. io1 is designed to deliver a consistent baseline performance of up to 50 IOPS/GB to a maximum of 64,000 IOPS and provide up to 1,000 MB/s of throughput per volume. Therefore, the io1 volume type would be able to meet the requirement of 25,000 IOPS per volume for the given use-case.

"Cold HDD (sc1)" - sc1 is backed by hard disk drives (HDDs). It is ideal for less frequently accessed workloads with large, cold datasets. It supports max IOPS/Volume of 250.

"Throughput Optimized HDD (st1)" - st1 is backed by hard disk drives (HDDs) and is ideal for frequently accessed, throughput-intensive workloads with large datasets and large I/O sizes, such as MapReduce, Kafka, log processing, data warehouse, and ETL workloads. It supports max IOPS/Volume of 500.
