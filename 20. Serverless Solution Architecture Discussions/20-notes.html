Lecture 1 · Mobile Application MyTodoList · PDF p. 495-500 (part p. 2-7)

MyTodoList: serverless REST API, Cognito, S3 access, duto caching layer

Shohoj kore: Ekta to-do app. Phone theke request jay ekta dorja (API Gateway) diye, bhitore karigor (Lambda) kaj kore, khata (DynamoDB) te likhe. Dorjar darwan (Cognito) dekhe tumi ke. Tomar nijer locker (S3 folder) khulte darwan tomake kichukkhon er chabi (temporary credentials) dey. Ar lok beshi porte ashle, ghon ghon prosno er uttor ekta notice board e (cache) likhe rakho.

Requirement (PDF p. 495 (part p. 2))

  • REST API, HTTPS endpoint.
  • Serverless architecture.
  • User nijer S3 folder e sorasori file rakhte / porte parbe.
  • User managed serverless service diye authenticate korbe.
  • User to-do likhe ar pore, kintu beshi pore (read heavy).
  • Database scale korbe, high read throughput chai.

Dhap 1: Serverless REST API layer (PDF p. 496 (part p. 3))

Dhap 1
Mobile client→ REST HTTPS API Gateway→ invoke Lambda→ query DynamoDB
Mobile client→ authenticate Cognito← verify authentication API Gateway

Classic serverless API. Client Cognito te login kore; API Gateway protita request e Cognito diye authentication verify kore.

  • API Gateway: REST + HTTPS endpoint (Section 19 e).
  • Lambda: API Gateway invoke kore; nije scale kore.
  • DynamoDB: serverless database, khub bhalo scale kore.
  • Cognito: serverless authentication; API Gateway er sathe directly integrated.
  • Instructor: "nothing new for you here", kintu exam e bar bar ashe.

Dhap 2: User ke nijer S3 folder e access (PDF p. 497 (part p. 4))

Dhap 2
Mobile client→ authenticate Cognitotemporary credentials dey→ permissions (credentials) Mobile client→ store / retrieve files Amazon S3shudhu nijer folder

Cognito temporary credentials generate kore client ke dey; oi credentials diye client sorasori S3 e jay, restricted policy soho.

  • Thik uttor: Cognito diye temporary credentials → S3 bucket e restricted policy (shudhu nijer jayga).
  • Bhul uttor: mobile app e AWS IAM user er credentials (access key) store kora. Instructor: "you definitely do not want to do this". Khub common question.
  • Section 19 er bhasay eta Cognito Identity Pools: user er token niye temporary AWS credentials, policy user_id diye customize (Section 19 e, PDF p. 491-492 (Section 19 part p. 51-52)).
  • Ei same pattern diye app DynamoDB, Lambda o sorasori access korte pare (PDF p. 500 (part p. 7)).
  • Temporary credentials pichone STS theke ashe amar jana, course e nai. Exam e "mobile user, temporary AWS credentials" dekhle uttor Cognito (Identity Pools).

Dhap 3: High read throughput, data kom bodlay → DAX (PDF p. 498 (part p. 5))

Dhap 3
API Gateway→ invoke Lambda→ query / read DAXcaching layer→ DynamoDBkom RCU lage

App boro hocche; pattern dekhlam: onek read (beshi RCU), to-do khub kom edit hoy. DynamoDB er thik shamne DAX.

  • Problem: read khub beshi → onek RCU → dam beshi.
  • Ki add: DAX (DynamoDB Accelerator) caching layer. Read gulo DAX e cache hoy.
  • Fol: DynamoDB te kom RCU lage → performance bare + cost kome. Enable kora khub easy.

Dhap 4: API Gateway level e response caching (PDF p. 499 (part p. 6))

Dhap 4
Mobile client→ REST HTTPS API GatewayCACHING OF RESPONSES→ cache miss hole Lambda→ DAX→ DynamoDB

Response gulo API Gateway tei cache; hit hole Lambda / DynamoDB porjonto jaoa-i lage na.

  • Kokhon: answer prai kokhono bodlay na, kichu API route er response cache kora jay.
  • DAX er sathe-o use kora jay (duita alada layer).
  • Ei architecture e kichui amra manage kori na, pay per usage; database management AWS er.

Official fact (course e nai): API Gateway caching stage e enable hoy, default TTL 300 s, max TTL 3600 s, cache ghonta hisebe charge hoy. Cache settings for REST APIs

Exam: "Fully serverless REST API" → API Gateway + Lambda (+ DynamoDB) (U20-Q1); ALB + EC2, ECS + EBS serverless na; CloudFront + S3 shudhu static. "Mobile user nijer S3 folder / temporary credentials" → Cognito, app e IAM access key kokhono na. "Read heavy DynamoDB, RCU / cost komao" → DAX. "Response bodlay na, stale data cholbe, backend (Lambda / Aurora) e load ar cost kom, minimal change" → API Gateway caching (S4-Q44); Aurora read replica = aro cost. Subtitle e "Amazon is free with temporary credentials" = "Amazon S3 with temporary credentials" dhorechi ("free" = S3, known error).

Lecture 2 · Serverless Website MyBlog.com · PDF p. 501-508 (part p. 8-15)

MyBlog.com: static site global + secure, public API, Global Tables, welcome email, thumbnail

Shohoj kore: Ekta blog: likha hoy kom (din e ba soptahe ekta), pora hoy onek (lakh lakh manush). Tai beshi tai static file, sara prithibir kache cache theke dao (CloudFront). Ektu dynamic part er jonno choto serverless API. Ar kichu "ghotona hole automatic kaj": notun user ashle welcome email, photo upload hole thumbnail. Sob serverless, kono server manage nai.

Requirement (PDF p. 501 (part p. 8))

  • Website globally scale korbe.
  • Blog kom likha hoy, onek pora hoy.
  • Website er kichu ongsho purely static files, baki ta dynamic REST API.
  • Jekhane somvob caching (cost + latency bachate).
  • Notun subscriber ke welcome email.
  • Upload kora protita photo er thumbnail generate.

MyTodoList er moto API, kintu public: tai Cognito nai. Read beshi tai DAX.

  • Read onek → DAX caching layer.

Dhap 4: DynamoDB Global Tables (PDF p. 505 (part p. 12))

Dhap 4

Dhap 5: User Welcome email flow (PDF p. 506 (part p. 13))

Dhap 5

Table e change hole stream → Lambda; Lambda er IAM role SES use korte dey; Lambda SDK diye email pathay.

  • Amazon SES = Simple Email Service: email pathanor service; Lambda AWS SDK diye call kore (detail Section 30 e).

Lecture 3 · MicroServices Architecture · PDF p. 509-511 (part p. 16-18)

Microservices: protita service nijer moto, sync vs async kotha bola

Shohoj kore: Ekta boro restaurant er bodole food court: protita dokan (service) nijer recipe, nijer chula, nijer staff. Ek dokan onno dokan ke sorasori dak dite pare ar uttor er jonno opekkha kore (sync), ba ekta order slip box e slip rekhe chole jay, pore keu kaj ta kore (async).

Requirement (PDF p. 509 (part p. 16))

  • Microservice architecture e jete chai.
  • Onek service ekjon arekjoner sathe REST API diye kotha bole.
  • Protita microservice er architecture alada form ar shape er hote pare.
  • Keno: protita service er leaner development lifecycle, independently scale, nijer code repository.

Microservices environment (PDF p. 510 (part p. 17))

Tin ta service, tin rokom design (ECS, serverless, classic EC2 + RDS). Protita service er nijer DNS name; Route 53 e query kore alias record pay.

  • Service 1: ELB → ECS (AWS e Docker container chalano, Section 18 e) → DynamoDB.
  • Service 2: API Gateway → Lambda → ElastiCache (DynamoDB er bodole; Lambda er backend ElastiCache o hote pare). Ei Lambda service 1 er ELB ke call kore.
  • Service 3: ELB → EC2 Auto Scaling → RDS (classic architecture). EC2 service 2 ke call kore (slide e dotted line).
  • Moral: protita microservice tumi je bhabe khushi design korte paro.

Exam: Microservices kotha bole sync (API Gateway, ALB, HTTPS) ba async (SQS, SNS, Kinesis, S3 → Lambda). "Reliable, retry, async, ekdin bondho rekhe porer din baki kaj theke shuru, protita job > 25 min" → SQS + EC2 (U20-Q6): Lambda max 15 min (Section 19), SQS message 14 din porjonto rakhe (Section 17), SNS message dhore rakhe na / retry queue nai, S3 → Lambda sathe sathe chale. "GB/s real-time data, onek consumer, replay" → Kinesis Data Streams (retention 365 din porjonto, Section 17) (U20-Q8); S3, Amazon MQ na.

Lecture 4 · Software updates distribution · PDF p. 512-515 (part p. 19-22)

Software update offloading: app na bodle shamne CloudFront

Shohoj kore: Notun game patch ber holo, sobai ek shathe download korte chay. Tomar ek dokane lomba line, server hapay, bandwidth bill uthe. Solution: patch er copy prithibir sob para-r dokane (edge location) rekhe dao. Manush kachakachi theke ney, tomar dokane chap kome. App er code ekdom bodlate hoy na.

Requirement (PDF p. 512 (part p. 19))

  • EC2 te ekta app, majhe majhe software update distribute kore.
  • Notun update ashle onek request, content network e mass distribute → khub dami.
  • App bodlate / re-architect korte chai na; shudhu cost ar CPU optimize.

Dhap 1: Current state (PDF p. 513 (part p. 20))

Ekhon
Usersupdate download→ ELBAZ 1 to 3→ ASGM5 EC2, AZ 1, 2, 3→ Amazon EFSupdate files

Classic ELB + ASG, multi-AZ. M5 instance gulo update distribute kore; simplicity er jonno update file gulo EFS e.

  • Problem: release e ASG onek scale kore → EC2, network, EFS cost beshi.

Dhap 2: Easy fix: CloudFront (PDF p. 514 (part p. 21))

Fix
Users→ CloudFrontedge e cache→ shudhu cache miss ELB→ ASG (EC2)→ EFS

Baki sob same; shudhu shamne CloudFront. Beshi request edge theke serve hoy.

Keno CloudFront (PDF p. 515 (part p. 22))

  • Architecture e kono change nai.
  • Software update file edge e cache hoy.
  • Update file dynamic na, static (kokhono bodlay na) → cache er jonno perfect.
  • EC2 serverless na, kintu CloudFront serverless, se nije scale korbe.
  • ASG kom scale korbe → EC2 e onek saving; network bandwidth, EFS cost, availability teo saving.
  • Existing app ke more scalable ar cheaper korar easy way, jodi content mostly static hoy. "Sometimes the best solution is the easiest one."
Exam: "EC2 / ALB / EFS theke boro static file (update, 15 GB image pack), monthly spike, EC2 load + network cost komao, without refactoring" → CloudFront distribution (ALB origin) (U20-Q7). ALB caching bole feature nai; EC2 scale up = aro cost, network cost same; S3 e shorano = refactor lage. Keyword: static + no change to app + cost → CloudFront.

Exam e ki mone rakhbo

Serverless API ar caching

  • "Fully serverless REST API" → API Gateway + Lambda (+ DynamoDB). ALB + EC2, ECS + EBS serverless na; CloudFront + S3 shudhu static (U20-Q1).
  • Built-in cache: API Gateway (response caching) ar DynamoDB (DAX) e ache; Lambda e nai (U20-Q2).
  • Read heavy DynamoDB, onek RCU, data kom bodlay → DAX (performance + cost).
  • Response bodlay na, stale data cholbe, backend DB (Aurora) cost beshi, minimal change → API Gateway caching; Aurora read replica = aro cost, "Lambda in-memory caching" nai, ALB e switch kore lav nai (S4-Q44). Official: default TTL 300 s, max 3600 s.

Cognito ar security

  • Mobile user nijer S3 folder / sorasori AWS resource → Cognito temporary credentials (Identity Pools), restricted policy. App e IAM user access key rakha = bhul uttor.
  • API Gateway + Cognito directly integrated (authentication verify). Public API (MyBlog) e Cognito lage na.
  • S3 shudhu CloudFront theke → OAC + bucket policy (CloudFront distribution allow); direct S3 access denied.
  • Lambda stream pore kintu SQS / SES / onno service e likhte pare na → Lambda execution role e permission nai. SQS e security group nai; Lambda SQS e likhte pare (U20-Q5).

Global static + dynamic website

  • Static S3 file globally → CloudFront; S3 CRR = copy, CDN na, dami; Route 53 = DNS; API Gateway = dynamic (U20-Q3).
  • Serverless + static + dynamic + onek desh → S3 (static) + Lambda + DynamoDB (dynamic) + CloudFront; EC2 / RDS option serverless na; S3 dynamic chalay na (S5-Q40).
  • Global data, kom latency, serverless → DynamoDB Global Tables; Aurora Global Database hoy kintu serverless na.
  • Global Table create er age enable → DynamoDB Streams (course answer; ekhon MREC e auto on) (U20-Q4). DAX, "Versioning", Backups na.
  • Notun user → welcome email → DynamoDB Streams → Lambda (IAM role) → SES. SES = Simple Email Service.
  • Photo upload → thumbnail → S3 event → Lambda → S3 (onno bucket hote pare). S3 event target: Lambda, SQS, SNS.
  • Upload druto: S3 Transfer Acceleration (edge location diye).

Microservices

  • Keno: leaner dev lifecycle, independent scale, nijer code repo. Protita service nijer moto design (ECS, Lambda, EC2 + RDS).
  • Sync = API Gateway, Load Balancer. Async = SQS, Kinesis, SNS, Lambda trigger (S3).
  • Challenge: repeated overhead, server density / utilization, onek version, client-side code. Serverless help: auto scale + pay per use, API clone / environment reproduce, Swagger theke client SDK.
  • Async, retry, pause ekdin → resume, job > 25 min → SQS + EC2; Lambda max 15 min; SNS message rakhe na; S3 → Lambda sathe sathe chale (U20-Q6).
  • GB/s real-time, multiple consumers, replay → Kinesis Data Streams; S3, Amazon MQ na (U20-Q8).

Software update offloading

  • EC2 + ELB + ASG + EFS, boro static file, release e spike, EC2 load + network cost, no refactor → CloudFront shamne (U20-Q7).
  • Distractor: "ALB caching" (nai), EC2 scale up (cost bare), S3 e move (refactor).
  • Fol: ASG kom scale → EC2, network, EFS cost kom; CloudFront serverless, nije scale.

Part A: Udemy course quiz (8)

The instructor's own section quiz: warm-up, direct questions. Answer first, then press Check.

A1U20-Q1Udemy quiz · sec 20 · Q1

A startup company plans to run its application on AWS. As a solutions architect, the company hired you to design and implement a fully Serverless REST API. Which technology stack do you recommend?

Correct: A. Why it is right

Fully serverless REST API er classic stack = API Gateway + Lambda (data lagle DynamoDB). API Gateway HTTPS REST endpoint dey, Lambda ke invoke kore; duita-i AWS manage kore, auto scale kore, pay per usage.

MyTodoList ar MyBlog.com duitai ei pattern e shuru (PDF p. 496 (part p. 3), PDF p. 504 (part p. 11)).

Why the other options are wrong

  • B. EC2 serverless na: instance tumi provision, patch, scale koro. ALB thakleo backend server-based.
  • C. ECS (EC2 launch type) ar EBS volume duita-i server / capacity manage kora jinish, serverless na.
  • D. CloudFront + S3 serverless thik, kintu shudhu static content serve kore; API er dynamic logic chalate pare na.

Keyword: fully Serverless REST API → API Gateway + Lambda

Instructor feedback (English)

A: This is fully serverless.

B: EC2 is not serverless.

C: Both ECS and EBS are not serverless.
