Lecture 10 + 11 (hands-on) · Amazon EKS · PDF p. 437-440 (part p. 22-25)

Amazon EKS: AWS e managed Kubernetes

Shohoj kore: Company already Kubernetes chalay (on-prem ba Azure/GCP)? Same Kubernetes API rekhe AWS e ashte chay → EKS. ECS er kaj same (container chalano), kintu API alada ar ECS open source na.

Overview (PDF p. 437 (part p. 22))

  • EKS = Elastic Kubernetes Service: AWS e managed Kubernetes cluster launch ar manage.
  • Kubernetes: open-source system, containerized (usually Docker) app er automatic deployment, scaling, management.
  • ECS er alternative: goal same, API alada. ECS open source na; Kubernetes open source, onek cloud provider use kore (standardization).
  • Duita mode: EC2 (worker node deploy) ba Fargate (serverless container).
  • Use case: company already Kubernetes use kore on-premises ba onno cloud e, Kubernetes diyei AWS e migrate korte chay.
  • Kubernetes cloud-agnostic (Azure, GCP ...): cloud er moddhe migration shohoj.
  • Multiple region: region proti ekta EKS cluster.
  • Log ar metric: CloudWatch Container Insights.

Diagram (PDF p. 438 (part p. 23))

  • VPC, 3 AZ, public + private subnet. Private subnet e EKS Worker Nodes (EC2), ASG manage kore.
  • Node er upor EKS Pods chale (ECS task er moto). "Pod" dekhle Kubernetes/EKS.
  • Service expose: public ba private load balancer (EKS Public / Private Service LB).

Node types (PDF p. 439 (part p. 24))

Self-Managed NodesTumiNije node banao, cluster e register, nijer ASG; beshi customization/control. EKS Optimized AMI (prebuilt) ba nijer AMI; On-Demand / Spot

Data Volumes (PDF p. 440 (part p. 25))

  • EKS cluster e StorageClass manifest dite hoy.
  • Container Storage Interface (CSI) compliant driver use kore (exam keyword).
  • Support: Amazon EBS, Amazon EFS (Fargate e kaj kore, Fargate er jonno eta-i ekmatro), FSx for Lustre, FSx for NetApp ONTAP.

Hands-on (dekhar jonno, free na)

  • Cluster create: Kubernetes version, cluster service role (IAM → EKS → "EKS cluster" use case), secrets KMS encryption option, VPC/subnet, SG, cluster endpoint access public, control plane logging option.
  • Cluster ready hole compute add: managed node group ba Fargate profile.
  • Node group er node IAM role (EC2 er jonno): AmazonEKSWorkerNodePolicy + AmazonEC2ContainerRegistryReadOnly. Tarpor AMI (Amazon Linux 2), On-Demand / Spot, instance type (t3.medium ...), disk, scaling (min/max/desired = ASG setting), update config (koyta node ek shathe down cholbe).
  • Add-ons: jemon Amazon EBS CSI driver (EBS use korte); EFS er jonnoo CSI driver ache.
  • Delete: age node group, tarpor cluster.
Exam:
  • "Already Kubernetes on-prem / multi-cloud / cloud-agnostic / open source" → EKS. "Pod" → EKS.
  • EKS node type: Managed Node Groups, Self-Managed Nodes, Fargate; Lambda na (U18-Q7).
  • EKS + Fargate e persistent storage → EFS (CSI driver). "StorageClass", "CSI" → EKS volume.
  • Multi-region → region proti ekta cluster. Monitoring → CloudWatch Container Insights.

Exam e ki mone rakhbo

ECS basics

  • Docker = container; use case microservices, lift-and-shift. ECS chalay Docker; Kubernetes = EKS; Mesosphere/OpenShift/Vagrant ECS na (B5-Q11).
  • ECS launch type: EC2 (tumi EC2 + ECS Agent) ar Fargate (serverless). "EKS launch type" bhul (U18-Q2). Real life e External + Managed Instances o ache.
  • "Don't provision / manage infrastructure, just run containers" → Fargate on ECS; EC2 launch type ba ECR na (U18-Q1).
  • Pricing: EC2 type = EC2 + EBS er dam, ECS er extra charge nai; Fargate = requested vCPU + memory (S1-Q14). "Duitai same", "ECS per hour" = bhul.
  • Long running web app → Service; batch → Task. Task definition e image, CPU/RAM, port, task role.

IAM

  • Container theke S3/DynamoDB/SQS → ECS Task Role (task definition e) (U18-Q3).
  • Notun app e authorization error, "proper security" → oi app er jonno notun task role; EC2 instance role e S3 add = shob task S3 pabe (least privilege bhange); Fargate on kora ba bucket policy edit = asol fix na (U18-Q5).
  • EC2 Instance Profile = ECS Agent: ECS API, ECR pull, CloudWatch Logs, Secrets Manager / SSM. Shudhu EC2 launch type.

Load balancer, storage

  • ALB = default (Fargate o). NLB = high throughput / PrivateLink. CLB = not recommended, Fargate na.
  • Microservice, host/path based URL, same container ek EC2 e onekbar, minimal maintenance → ALB + dynamic port mapping; CLB/NLB + dynamic port, reverse proxy = bhul (S4-Q57).
  • Shared content (WordPress files), multi-AZ, persistent, EC2 + Fargate → EFS; EBS (ek instance/AZ, task proti ekta notun), instance store (ephemeral) na (U18-Q4). Fargate + EFS = serverless.
  • Slide e notun: S3 Files = S3 bucket file system hishebe, Fargate / Managed Instances, EC2 type na.

Scaling, architectures

  • ECS Service Auto Scaling = Application Auto Scaling; metric: CPU, Memory, ALB RequestCountPerTarget; Target Tracking / Step / Scheduled.
  • Task scaling ≠ EC2 scaling. EC2 type e instance add → ECS Cluster Capacity Provider (ASG er sathe paired), ASG scaling er cheye smart. Fargate e shudhu task scale.
  • S3 upload → EventBridge rule → ECS task (Fargate) + task role → DynamoDB. Hourly batch → EventBridge schedule. SQS queue → ECS service + Service Auto Scaling. Task stopped → EventBridge → SNS email.
  • Static SPA, serverless, HTTPS, low latency, cheap → S3 + CloudFront; Fargate/EC2 overkill (S5-Q60).

ECR, EKS, App Runner, A2C

  • "Store Docker images", Docker Hub alternative, ECS integrated → ECR (U18-Q6). Private + Public Gallery, S3 backed, IAM (pull error → policy), vulnerability scan, lifecycle.
  • "Already Kubernetes on-prem / other cloud", "cloud-agnostic", "pods" → EKS. Region proti ekta cluster; CloudWatch Container Insights.
  • EKS node: Managed Node Groups, Self-Managed Nodes, Fargate; Lambda na (U18-Q7).
  • EKS storage: StorageClass + CSI driver; EBS, EFS (Fargate e shudhu eta), FSx Lustre, FSx NetApp ONTAP.
  • "Developer new to AWS, website + API container, easiest" → App Runner; EC2 + ALB, ECS, Fargate = beshi kaj (U18-Q8). Real life: notun customer bondho → ECS Express Mode.
  • "Java / .NET web app, containerize, no code change, lift-and-shift" → App2Container (→ ECR → ECS/EKS/App Runner, CloudFormation).

B4S5-Q60Stephane set 5 · Q60Design High-Performing Architectures

A solutions architect is tasked with a requirement to design a low-latency solution for a static, single-page application, accessed by users through a custom domain name. The solution must be serverless, provide in-transit data encryption and needs to be cost-effective.

Which AWS services can be combined to build a solution for the company's requirement?

Correct: C. Why it is right

Static single-page app: server-side compute lage na. S3 static website hosting e file rakho, samne CloudFront: edge location e cache kore low latency, custom domain e HTTPS (S3 website endpoint nije HTTPS dey na). Duitai serverless ar cost-effective (Section 12, 15).

Why the other options are wrong

  • A. EC2 serverless na, ar instance store ephemeral; static site er jonno server chalano beshi cost ar ops.
  • B. Static content er jonno Fargate container chalano overkill, extra cost; S3 nijei static site serve kore. Low latency (CDN) o nai.
  • D. Fargate + ELB static SPA er jonno onek beshi jinish ar dam; ELB global low latency o dey na, CloudFront dey.

Keyword: static SPA + serverless + in-transit encryption + low latency + cost-effective → S3 + CloudFront

Original explanation (English)

Correct option:

Amazon S3 can be used to host the static website. While Amazon CloudFront can be used to distribute the content for low latency access

To host a static website on Amazon S3, you configure an Amazon S3 bucket for website hosting and then upload your website content to the bucket. When you configure a bucket as a static website, you must enable website hosting, set permissions, and create and add an index document. Depending on your website requirements, you can also configure redirects, web traffic logging, and a custom error document.

After you configure your bucket as a static website, you can access the bucket through the AWS Region-specific Amazon S3 website endpoints for your bucket. Website endpoints are different from the endpoints where you send REST API requests. Amazon S3 doesn't support HTTPS access for website endpoints. If you want to use HTTPS, you can use CloudFront to serve a static website hosted on Amazon S3.

You can use Amazon CloudFront to improve the performance of your website. CloudFront makes your website files (such as HTML, images, and video) available from data centers around the world (called edge locations). When a visitor requests a file from your website, CloudFront automatically redirects the request to a copy of the file at the nearest edge location. This results in faster download times than if the visitor had requested the content from a data center that is located farther away.

CloudFront caches content at edge locations for a period of time that you specify. If a visitor requests content that has been cached for longer than the expiration date, CloudFront checks the origin server to see if a newer version of the content is available. If a newer version is available, CloudFront copies the new version to the edge location. Changes that you make to the original content are replicated to edge locations as visitors request the content.

Incorrect options:

Host the application on Amazon EC2 instance with instance store volume for high performance of the application to provide low latency access to users - Since the use case speaks about a serverless solution, Amazon EC2 cannot be the answer, since EC2 is not serverless.

Host the application on AWS Fargate and front it with an Elastic Load Balancer for an improved performance - AWS Fargate is a serverless compute engine for containers that works with both Amazon Elastic Container Service (ECS) and Amazon Elastic Kubernetes Service (EKS). Elastic Load Balancer can spread the incoming requests across a fleet of EC2 instances. This added complexity is not needed since we are looking at a static single-page webpage.

Configure Amazon S3 to store the static data and use AWS Fargate for hosting the application on serverless architecture - Fargate is overkill for hosting a static single-page webpage.
